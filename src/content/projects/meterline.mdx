## Problem

Usage-priced SaaS ("pay per token", "pay per API call") needs a backend that counts every event exactly once, answers "is this customer over their limit?" in milliseconds, and bills through Stripe without ever disagreeing with Stripe. OpenMeter, Lago and Orb sell this. I want to understand it by building it.

## What it will do

A SaaS company runs Meterline next to its own app with `docker compose up` and its own Stripe keys. Meterline never holds anyone's money, cards or data.

## Design decisions so far

- **A modular monolith with two deployables** (API and worker) on one Postgres database. One team and one database make microservices pure overhead.
- **Postgres only in v1, no message broker.** Background work uses `FOR UPDATE SKIP LOCKED`. A broker gets added only if a k6 load test proves Postgres can't keep up.
- **Atomic consume in Redis with a Lua script**, so two concurrent requests can't both spend the last of a quota.
- **A hand-rolled transactional outbox and inbox**, so at-least-once delivery never means double counting.
- **Stripe in test mode only**, with a live dashboard over SignalR.

## Hard parts I expect

Correctness under concurrency, late events that arrive after a billing window closes, Stripe webhooks that arrive out of order, and proving all of that with a failing test per failure mode before writing the fix.
